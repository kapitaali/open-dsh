# RR-W22 — Connection profiles for the dsh fork

**Date:** 2026-11-14 · **Branch:** `connection-profiles` · **Base:** `master` (release 0.2.2-rc.3)
**Status:** implemented, gates green, uncommitted at time of writing

---

## 1. What this is

A fork feature for the DeepSeek Harness: **connection profiles**. The default profile keeps the
default DeepSeek connection; a custom profile can be given an API endpoint URL and an API key
and connects there instead.

The default profile is untouched — with no patch row, the `llm-deepseek` plugin still falls back
to `$DEEPSEEK_BASE_URL` / `DEEPSEEK_API_KEY` / `https://api.deepseek.com/anthropic`. A custom
connection is applied by writing the `llm-deepseek` row's `config` (`baseURL` + `apiKeyEnv`)
into that profile's own `cordis.patch.yml`.

Plans of record: `design/W22-DSH-CONNECTIONS-20261114.md`, `design/W22-DSH-ADAPTER-20261114.md`.

## 2. What was built

### 2.1 New package — `packages/util/connection-store/`

`@deepseek-ai/dsh-connection-store` (kind `package-reference`):

- `$DSH_HOME/connections.yaml` — a versioned YAML document holding named connections
  (`name`, `baseURL`, `apiKeyEnv`). No secret value lives in it.
- Strict parse: a malformed document, unknown version, duplicate name, or a field outside its
  grammar throws rather than being skipped. An absent document is an empty store.
- `storeConnectionKey` / `removeConnectionKey` — edit the credential store's `refs` section
  with the same comment-preserving, locked, atomic write the credentials provider uses
  (mode `0600`, dir `0700`).
- Registered in `tsconfig.host.json`, `apps/cli/tsconfig.json`, `tsconfig.base.json`
  (via `pnpm run gen-tsconfig-paths`), and `packages/util/README.md`.

### 2.2 CLI — `dsh connection`

| Command | Effect |
|---|---|
| `dsh connection add <name> --url <url> --key <key>` | Save a connection + its API key |
| `dsh connection use <profile> <name>` | Apply a connection to a profile's patch |
| `dsh connection list` | List saved connections |
| `dsh connection show <name>` | Show one connection |
| `dsh connection remove <name>` | Remove a connection + its key |
| `dsh connection create <profile> --url <url> --key <key>` | Create a profile with a connection |

Flags: `--route deepseek|pi-ai` (default `deepseek`), `--model`, `--api`, `--context-window`.

A `deepseek` connection writes the `llm-deepseek` row's config (Anthropic Messages wire). A
`pi-ai` connection merges one provider route into the `llm-pi-ai` row and points
`agent-default-model` at it, which reaches OpenAI-compatible and other wires.

Wiring: `ConnectionInvocation` + commander subcommand in `apps/cli/src/args.ts`, dispatch in
`apps/cli/src/bin.ts`, examples in the launcher help. `apps/cli/src/connection.ts` reproduces
the config-editor's patch write (comments and `!!js` preserved, atomic `0600`).

### 2.3 Importing Hermes credentials

`pnpm run setup:hermes` asks where Hermes is installed (default `~/.hermes`), reads its `.env`,
writes the credential-shaped entries into the dsh credential store, and turns each recognised
provider key into a connection using the provider's catalog endpoint
(`scripts/import-hermes-credentials.ts`; `PROVIDER_DATA` is exported from `llm-pi-ai` for this).
Values are never printed.

Live run against the user's `~/.hermes` (isolated `DSH_HOME`): 6 keys imported, and 4 connections
created — `openrouter`, `nvidia`, `deepseek`, and **`nous`** (from `auth.json`, endpoint
`https://inference-api.nousresearch.com/v1`). `pnpm run refresh:connections nous` then listed
**401 models** from that endpoint.

Nous is not in pi-ai's catalog, so the import reads Hermes's `auth.json` portal logins as well as
`.env`: any `providers.<id>` with an `inference_base_url` and an `access_token` becomes a
connection whose credential reference is `<ID>_ACCESS_TOKEN`. That token is an OAuth inference JWT
with a short lifetime, so a Nous connection needs re-importing (or a Hermes refresh) as it expires.

A `pi-ai` connection no longer requires a model: without one the route defers to the installed
catalog, so `dsh connection add` also accepts `--key` being omitted once the reference is stored.

### 2.4 Refreshing the model catalog

`pnpm run refresh:connections` (`scripts/refresh-connection-catalog.ts`) asks each `pi-ai`
connection's endpoint for its model list and stores the ids on the connection, so
`dsh connection use` can write them into the profile's provider route. Default is the endpoint
itself (`GET {baseURL}/models` through `dsh-llm-pi-ai` `discoverModels`); `--prefer-catalog`
answers known providers from the installed registry instead. `--dry-run` previews, names limit
the run, and `deepseek`-route connections have no endpoint listing and are skipped.

Live run on the imported connections: `openrouter` 471 models, `nvidia` 83 models,
`deepseek` skipped. The connection document gained a `models` list (round-tripped and
validated in the store spec); `readConnectionKey` was added as the read-only counterpart of
`storeConnectionKey`.

### 2.5 Docs

`docs/cli-help.md` / `.zh.md` regenerated with a `## dsh connection` section

### 2.6 Applying a connection to a profile

`dsh connection use <profile> <name>` creates the profile directory when it is missing, and
`--from-default-profile <web|headless|sdk|acp>` gives the new profile that template's application
bundles — without it the profile carries only the base composition and has no server to boot.

Verified end to end on the Nous route:

```
pnpm dsh connection add nous-luna --url https://inference-api.nousresearch.com/v1 \
  --key <NOUS_ACCESS_TOKEN> --route pi-ai --model openai/gpt-6-luna
pnpm dsh connection use nh2 nous-luna --from-default-profile headless
pnpm dsh --profile nh2 "Reply with exactly: OK"      # → OK
```

The earlier hang on this route was an **expired Nous inference JWT** (the portal token lives about
an hour); `hermes auth refresh nous` clears it. A dead token makes the request stall rather than
fail fast — worth a fast-fail guard.

### 2.7 Reasoning effort switch

`packages/interaction/command-reasoning` registers `/reasoning` (mounted in the base bundle):

- `/reasoning show` (or no argument) reports the current provider, model, and effort.
- `/reasoning <level>` re-selects the same provider and model with that effort, so the change is
  durable for the session's later steps and is recorded as a `model/selection` event.

Levels accepted are the union adapters use (`off`, `none`, `minimal`, `low`, `medium`, `high`,
`xhigh`, `max`, `ultra`); anything else is forwarded rather than guessed at, because only the
adapter holding the per-model effort table can validate it. The command never reaches the model.

## 5. Limitations and open questions

- **No npm distribution yet.** The feature lives in the fork's tree; the release path (npm
  package, tarball, or run-from-source) is an owner decision.
- **No settings UI.** Connections are CLI-only so far; the Web Settings page does not manage
  them.
- **`--key` on the command line** is visible in shell history. A prompt-based input (like the
  Models page) is the alternative.
- **The connection document does not preserve hand-written comments** across a write; it is
  machine-managed.
- **No runtime reader.** The harness runtime resolves the resulting `llm-deepseek` config; it
  never reads `connections.yaml`.
- **W22 adapter (ctxvm trace capture) is design-only** in this commit; only the connection
  feature is implemented.

## 5. Changes since the initial report (2026-11-15)

### 5.1 `reasoningEfforts` on every connection model

Added `reasoningEfforts?` to the `Connection` type (`packages/util/connection-store/src/index.ts`),
a map of effort level → wire spelling (`off: null`, `low: 'low'`, `high: 'high'`, `max: 'max'`)
that is parsed, serialized, and round-tripped through `connections.yaml`.

- **`scripts/refresh-connection-catalog.ts`**: when refreshing a connection that lacks
  `reasoningEfforts`, adds the default set `{ off: null, low: low, high: high, max: max }`
  and prints `(added default reasoning efforts)`. `deepseek`-route connections are still
  skipped (no endpoint listing).
- **`apps/cli/src/connection.ts`** (`applyPiAiConnection`): propagates the connection's
  `reasoningEfforts` into every model entry written to the profile's `llm-pi-ai` patch row,
  so the model picker's Effort row appears for custom providers like `nous` whose hand-declared
  models carry no reasoning metadata.
- **Verification**: refreshed all 3 `pi-ai` connections — `openrouter` (470 models),
  `nvidia` (83), `nous` (400). The `nous` profile patch now carries `reasoningEfforts: *a2`
  (YAML anchor) on every model entry including `meituan/longcat-2.5:free`.

### 5.2 Apply all connections to profiles on `setup:hermes`

Extended `scripts/import-hermes-credentials.ts` so that after importing credentials and
creating connections, every saved connection is automatically applied to a profile of the
same name — no separate `dsh connection use <profile> <name>` per connection needed.

- **`packages/util/connection-store/src/index.ts`**: extracted `applyConnectionToProfile`
  (writes `llm-deepseek` / `llm-pi-ai` / `agent-default-model` into a profile patch with
  comment-preserving, locked atomic writes) and `ensureProfileForConnection` (inits the
  profile from a template then applies the connection), shared by the CLI and the setup
  script. Added peer deps `dsh-app-boot` and `dsh-official-bundles`, plus tsconfig
  references.
- **`scripts/import-hermes-credentials.ts`**: after writing connections, inits and applies
  each connection to its matching profile (default `web` template). Existing connections are
  preserved — setup no longer clobbers a connection that already carries models and
  `reasoningEfforts` from `refresh:connections`.
- **`apps/cli/src/connection.ts`**: refactored to import `applyConnectionToProfile` from the
  connection-store instead of duplicating the YAML patch logic; removed the now-unused
  `DEFAULT_PROFILE_TEMPLATE` constant.

Live run against `~/.hermes` + `~/.dsh`: 6 credentials imported (OPENROUTER_API_KEY,
